Task T2.17 (#104), the speed and the health of the checks. The full tier failed on `main` because the JAX float64 job ran out of memory on CI's 16 GB runners: each test worker is one JAX process, which kept every compiled program in memory, and four workers filled the memory and the swap. The JAX run now drops the compiled programs kept in memory after each test (they stay in the compilation cache on disk): the peak of the job goes from 15.9 GB to 4.9 GB, with no change to any test. CI: the two required checks, `make check` and `make check (jax)`, run the fast tier in every run; the full tier runs in jobs of its own, `full tier (torch)`, `full tier (jax, float64, part 1 of 2)`, `full tier (jax, float64, part 2 of 2)` and `full tier (jax, float32)`, which a pull request labelled `full-ci` shows without being blocked by them; the float64 run is split in two parts (`make test TEST_SHARD=1/2`, `ESTEL_TEST_SHARD`), disjoint and together complete; a push runs the workflow on `main` only, so a pull request runs it once per push instead of twice. Locally: mypy's cache and JAX's compilation cache are shared by every worktree of the machine, in `~/.cache/estel` (`ESTEL_CACHE_DIR`), and `make` lets Python write its bytecode in agent sessions; the first `make check` of a new worktree goes from 25 to 31 s to about 22 s. Specification edits at the maintainer's request: the row of T2.17 (`docs/transfer/part2.md`) and the two tiers of Part I, §5.4 as CI now runs them (`docs/transfer/part1.md`). A fast-tier test checks that every test ID belongs to exactly one part of the split. No test is removed, skipped, weakened or moved between tiers; no time limit, budget, statistic, public name or reference value changes.
