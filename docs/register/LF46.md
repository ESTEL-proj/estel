## Goal

Syntheses, and any loss that ends the computation, take their gradient on PyTorch with about 30 % less memory; `value_and_grad` stays composable, for implicit differentiation and the second order.

## Inputs

Part I §3.2.2 to §3.2.4; Part II §12.3 (`value_and_grad`), §12.9 (`run_lbfgs`), §15.2, T2.14 and the prototype of issue #92; Part IV §22, "Global optimisations only in 1.0.0"; maths_step2 M-GRAD (what automatic differentiation keeps); maths M-SYN-LBFGS.
Modules: `src/estel/backend/_protocol.py` (`value_and_grad`), `src/estel/backend/torch/_primitives.py`, `src/estel/backend/jax/_primitives.py`, `src/estel/backend/torch/_optim.py`, `estel/synthesis/` (`run_lbfgs`), `tests/backend/test_conformance.py`.

## Tasks

1. The internal L0 primitive `value_and_grad_first_order(fn)`: on PyTorch by `torch.autograd.grad` without `create_graph`, on JAX the same as `value_and_grad`; conformance tests on both backends.
2. Syntheses call it; the peak memory with the gradient and the time per iteration of a 2D synthesis, before and after, in the pull request.

## Done when

Conformance: the value and the gradient equal those of `value_and_grad` on both backends, in float32 and float64, and on PyTorch the gradient carries no graph; a synthesis gives the same field as before within the float64 tolerance, with a lower peak memory on PyTorch (about 30 % in T2.14); the second-order tests are unchanged.

## Feature

A first-order gradient for a loss that ends the computation, as in a synthesis: a primitive `value_and_grad_first_order`, by `torch.autograd.grad` on PyTorch, whose result is not differentiated again; `value_and_grad` stays composable, for implicit differentiation and the second order

## Why

about 30 % less memory with the gradient on PyTorch (prototype of T2.14, issue #92); the use of order-1 engines (Part I, §3.2.4)

## Builds on (reserved in 1.0.0)

the L0 protocol
